# Отчет: аномалии изоляции в SQL

## 1. Выбранная СУБД

Для практики используется MySQL 8.4 с движком InnoDB. MySQL выбран потому, что он позволяет на практике показать все четыре требуемые аномалии при разных уровнях изоляции и некорректном способе обновления данных.

## 2. Выбранные аномалии

В работе воспроизведены:

- `dirty read`;
- `non-repeatable read`;
- `phantom read`;
- `lost update`.

Скрипт создания таблиц и тестовых данных находится в `sql/00_schema.sql`. Ручные сценарии по двум SQL-сессиям находятся в файлах `sql/01_dirty_read.sql` - `sql/04_lost_update.sql`.

## 3. Dirty read

Dirty read - это чтение данных, которые были изменены другой транзакцией, но еще не зафиксированы через `COMMIT`.

### Шаги воспроизведения

1. Таблица `accounts` содержит строку `id = 1`, `balance = 100`.
2. Сессия A открывает транзакцию и выполняет `UPDATE accounts SET balance = 50 WHERE id = 1`, но не делает `COMMIT`.
3. Сессия B работает на уровне `READ UNCOMMITTED` и читает `balance`.
4. Сессия A выполняет `ROLLBACK`.
5. Сессия B повторно читает `balance`.

### Полученный результат

Сессия B увидела значение `50`, хотя оно не было зафиксировано. После `ROLLBACK` в таблице осталось `100`.

Фрагмент лога:

```text
== DIRTY READ ==
A: UPDATE accounts SET balance = 50, COMMIT еще не выполнен.
B: SELECT balance -> 50
A: ROLLBACK
B: повторный SELECT balance -> 100
Результат: B прочитала 50, хотя после ROLLBACK в таблице снова 100.
```

### Как избежать

Не использовать уровень `READ UNCOMMITTED`. Для MySQL достаточно перейти на `READ COMMITTED` или более строгий уровень изоляции.

## 4. Non-repeatable read

Non-repeatable read - это ситуация, когда в рамках одной транзакции повторное чтение той же строки возвращает другое значение, потому что другая транзакция успела изменить и зафиксировать эту строку.

### Шаги воспроизведения

1. Таблица `products` содержит строку `id = 1`, `price = 100`.
2. Сессия A открывает транзакцию на уровне `READ COMMITTED` и читает `price`.
3. Сессия B изменяет `price` на `120` и делает `COMMIT`.
4. Сессия A повторно читает ту же строку в той же транзакции.

### Полученный результат

Первое чтение вернуло `100`, второе чтение вернуло `120`.

Фрагмент лога:

```text
== NON-REPEATABLE READ ==
A: первый SELECT price -> 100
B: UPDATE price = 120; COMMIT
A: второй SELECT price в той же транзакции -> 120
Результат: одна и та же строка изменилась с 100 на 120.
```

### Как избежать

Использовать `REPEATABLE READ` или `SERIALIZABLE`, либо блокировать нужную строку через `SELECT ... FOR UPDATE`, если данные далее будут использоваться для принятия решения или изменения.

## 5. Phantom read

Phantom read - это ситуация, когда повторный запрос по условию в рамках одной транзакции возвращает другой набор строк из-за вставки или удаления строк другой транзакцией.

### Шаги воспроизведения

1. В таблице `orders_demo` есть один заказ со статусом `NEW`.
2. Сессия A на уровне `READ COMMITTED` выполняет `SELECT COUNT(*) FROM orders_demo WHERE status = 'NEW'`.
3. Сессия B вставляет новый заказ со статусом `NEW` и делает `COMMIT`.
4. Сессия A повторяет тот же запрос в той же транзакции.

### Полученный результат

Первый запрос вернул `1`, второй запрос вернул `2`.

Фрагмент лога:

```text
== PHANTOM READ ==
A: первый COUNT(status='NEW') -> 1
B: INSERT нового заказа со status='NEW'; COMMIT
A: второй COUNT(status='NEW') в той же транзакции -> 2
Результат: появился фантомный заказ, счетчик изменился с 1 на 2.
```

### Как избежать

Использовать `REPEATABLE READ` или `SERIALIZABLE`. В MySQL/InnoDB также помогают блокирующие чтения по индексированному условию, например `SELECT ... FOR UPDATE`, потому что InnoDB применяет next-key locks и блокирует появление строк в нужном диапазоне.

## 6. Lost update

Lost update - это потерянное обновление, когда две транзакции читают одно и то же значение, независимо вычисляют новое значение и затем записывают его обратно. Второй `UPDATE` затирает результат первого.

### Шаги воспроизведения

1. Таблица `counters` содержит строку `id = 1`, `value = 10`.
2. Сессия A читает `value = 10` и на стороне приложения вычисляет `11`.
3. Сессия B тоже читает `value = 10` и вычисляет `11`.
4. Сессия A записывает `11` и делает `COMMIT`.
5. Сессия B записывает `11` и делает `COMMIT`.
6. Проверяется итоговое значение.

### Полученный результат

Итоговое значение равно `11`, хотя после двух увеличений должно быть `12`.

Фрагмент лога:

```text
== LOST UPDATE ==
A: SELECT value -> 10; приложение вычисляет 10 + 1 = 11
B: SELECT value -> 10; приложение вычисляет 10 + 1 = 11
A: UPDATE counters SET value = 11; COMMIT
B: UPDATE counters SET value = 11; COMMIT
Итоговое значение -> 11
Результат: ожидалось 12, но одно обновление потеряно, в таблице 11.
```

### Как избежать

Не делать обновление по устаревшему значению, рассчитанному в приложении. Безопасные варианты:

- атомарное обновление: `UPDATE counters SET value = value + 1 WHERE id = 1`;
- блокировка строки перед чтением: `SELECT value FROM counters WHERE id = 1 FOR UPDATE`;
- оптимистическая блокировка через колонку `version`;
- более строгий уровень изоляции `SERIALIZABLE` с обработкой ошибок конкурентного доступа.

## 7. Вывод

Практика показывает, что при параллельной работе с базой данных результат зависит от уровня изоляции и способа записи данных. Для предотвращения аномалий нужно выбирать подходящий уровень изоляции, использовать блокирующие чтения для критичных строк и применять атомарные SQL-операции вместо вычисления новых значений на стороне приложения.
