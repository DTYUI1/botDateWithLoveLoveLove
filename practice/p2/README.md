# P2 — Сравнение RabbitMQ и Redis как брокеров сообщений

## Цель

Прогнать одинаковую нагрузку через `RabbitMQ` и `Redis` и измерить:

- пропускную способность (`msg/sec`);
- среднюю и p95 задержку;
- количество потерянных сообщений;
- момент, когда `single instance` начинает деградировать;
- потребление CPU и RAM брокером.

## Архитектура стенда

```
┌───────────────┐      ┌──────────────┐      ┌───────────────┐
│  producer (1) │ ───▶ │   broker     │ ───▶ │  consumer (1) │
│  (bench ctr)  │      │ (rmq | redis)│      │  (bench ctr)  │
└───────────────┘      └──────────────┘      └───────────────┘
         ▲                     ▲                      │
         │                     │ docker stats         │ latency = now - sent_at
         └──────── runner orchestrator ───────────────┘
```

Все три части (`producer`, `broker`, `consumer`) запущены в Docker Compose. `producer` и `consumer` живут в одном bench-контейнере, брокер меняется между прогонами автоматически. `docker stats` подключён через монтирование `docker.sock` — bench-контейнер сам снимает CPU/RAM обоих брокеров.

## Что внутри

| Файл | Назначение |
|------|-----------|
| `docker-compose.yml` | Поднимает `rabbitmq`, `redis`, `bench` |
| `Dockerfile` | Python 3.13 + `docker-cli` (для `docker stats`) |
| `bench/config.py` | Матрица экспериментов (размеры, скорости, длительность) |
| `bench/message.py` | Формат сообщения: `{id, sent_at, payload}` — `payload` добивается до нужного размера |
| `bench/metrics.py` | Счётчики и расчёт p95 |
| `bench/rabbit.py` | Async producer/consumer через `aio_pika` (durable queue, NOT_PERSISTENT, manual ack) |
| `bench/redis_bench.py` | Async producer/consumer через `redis-py` (`RPUSH` / `BLPOP`) |
| `bench/docker_stats.py` | Раз в секунду дергает `docker stats --no-stream`, пишет CSV |
| `bench/runner.py` | Orchestrator: крутит матрицу, печатает таблицу, сохраняет CSV |

## Настройка параметров через env

Все параметры можно переопределить через переменные окружения в `docker-compose.yml`:

```yaml
environment:
  BENCH_DURATION: "30"               # секунды на прогон
  BENCH_SIZES: "128,1024,10240,102400"   # байты
  BENCH_RATES: "1000,5000,10000"     # msg/sec
```

Пример быстрой отладки (2 прогона вместо 24):
```yaml
BENCH_DURATION: "5"
BENCH_SIZES: "1024"
BENCH_RATES: "1000,5000"
```

## Метрики и как они считаются

| Метрика | Как считается |
|---------|---------------|
| `sent` | Счётчик удачных публикаций на стороне producer |
| `received` | Счётчик полученных сообщений на стороне consumer |
| `lost%` | `(sent - received) / sent * 100` |
| `throughput` | `received / duration` |
| `avg_ms` | Среднее от `now - sent_at` по всем полученным сообщениям |
| `p95_ms` | 95-й перцентиль того же распределения |
| `cpu_pct` | Среднее `docker stats` за прогон по контейнеру брокера |
| `mem_mb` | Пик памяти контейнера брокера за прогон |
| `status` | `OK` / `DEGRADED` / `ERROR` — см. ниже |

**Правило деградации** (помечается `DEGRADED`, если сработало хотя бы одно):
- потери > 5% (`received < sent * 0.95`);
- p95 > 500 ms;
- фактический throughput < 80% от целевого.

## Методология — почему так

- **Одинаковые условия для обоих брокеров.** Один и тот же формат сообщения, один producer, один consumer, одна и та же машина, одна и та же длительность. Меняется только бэкенд.
- **Single instance.** ТЗ прямо требует найти точку деградации single instance, поэтому кластер не поднимаем.
- **Redis = List + RPUSH/BLPOP.** Это самый типовой паттерн «Redis как очередь» — быстрый, in-memory, без персистентности. Альтернатива — Redis Streams (ближе по семантике к RabbitMQ, с персистентностью и consumer groups), но тогда сравниваются разные классы решений. Упомянуто намеренно.
- **RabbitMQ = durable queue + NOT_PERSISTENT delivery mode.** Очередь объявлена `durable=True` (честный прод-сетап), но сами сообщения не требуют записи на диск — чтобы сравнение с Redis List (тоже в памяти) было «по делу».
- **Rate limiting.** Producer держит темп через `next_send += 1/rate`. Если брокер тормозит — producer упрётся в `await publish` и начнёт отставать от плана. Это и есть деградация.
- **p95, а не max.** Max чувствителен к одиночному выбросу (например, GC-пауза). p95 лучше отражает реальную картину.
- **Producer и consumer в одном контейнере.** Так они делят CPU с runner'ом, но **одинаково** для обоих брокеров — поэтому соотношение корректно, даже если абсолютные числа меньше, чем на «голом» железе.

## Конфликт портов с основной инфрой проекта

У проекта `connectme` уже есть свои `redis` и `rabbitmq` на стандартных портах (`6379`, `5672`, `15672`). Чтобы не ломать её, стенд p2:

- не публикует наружу ни `5672` (AMQP), ни `6379` — bench-контейнер ходит к брокерам по внутренней docker-сети по hostname `rabbitmq` / `redis`;
- публикует RabbitMQ UI на **`15673`** (чтобы не биться с `15672` основной инфры).

Поэтому запускать p2 можно, **не останавливая** основной проект.

## Ограничения

- Один физический хост — producer, consumer, брокер делят CPU и сеть.
- Абсолютные значения `throughput` и `latency` привязаны к железу. Важны **соотношения**.
- На `10 000 msg/sec` точность rate-limiter ограничена разрешением event loop (обычно достаточно).
- RabbitMQ с `NOT_PERSISTENT` быстрее, чем с `PERSISTENT`. Если нужна честная сравка с дисковой Redis Stream — перепишите в `rabbit.py` и сравните заново.

## FAQ

**Q: Почему `docker stats` для брокера, а не `rabbitmq-diagnostics` / `INFO`?**
A: Чтобы метрики снимались одинаково для обоих брокеров. Проще и честнее.

**Q: Что если нет прав на `docker.sock`?**
A: Уберите монтирование `docker.sock` в `docker-compose.yml` — CPU/RAM колонки будут нули, всё остальное продолжит работать.

**Q: Как быстро прогнать только одну комбинацию для отладки?**
A: См. пример в «Настройка параметров через env» выше.
