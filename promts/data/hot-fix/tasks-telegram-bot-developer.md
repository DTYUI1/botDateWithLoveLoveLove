# Hot-fix задача для Telegram Bot Developer

**Дата:** 2026-05-12  
**Роль:** `promts/telegram_bot_developer.md`  
**Приоритет:** высокий  
**Зона:** Telegram UX / aiogram handlers  

---

## 1. Проблема

Бот засоряет чат: при навигации по профилю, фото, поиску и настройкам он почти
каждое состояние отправляет новым сообщением через `message.answer(...)` /
`callback.message.answer(...)`, вместо того чтобы обновлять уже показанный
экран.

Реальный пример из проверки:

- `/start` открывает фото-flow.
- При переходах `Мои фото`, просмотр фото, назад к фото, профиль, повторный
  список фото, загрузка фото, `/search`, `/settings` бот создаёт много новых
  сообщений подряд.
- Для пользователя это выглядит как мусорная лента, хотя фактически это один
  UI-сценарий.

Цель hot-fix: перевести основные screen-like сценарии бота на обновление
последнего сообщения, а новые сообщения оставлять только там, где Telegram API
или UX действительно требуют нового сообщения.

---

## 2. Что нужно сделать

### 2.1 Ввести единый helper для "экрана" бота

Добавить небольшой helper, например:

- `bot/utils/message_editor.py`

Он должен уметь:

- безопасно редактировать текст текущего callback-сообщения через
  `edit_text(...)`;
- безопасно редактировать caption/media-сообщения, где это возможно;
- если редактирование невозможно (`TelegramBadRequest: message is not modified`,
  media/text mismatch, сообщение удалено, старое сообщение нельзя редактировать)
  — fallback на `answer(...)`;
- опционально удалять временное сообщение-статус (`⏳ Загружаю фото...`,
  `🔍 Ищу...`) после завершения операции;
- не падать наружу из handler'а из-за невозможности edit/delete.

Минимальный API helper'а:

```python
async def replace_message(message_or_callback_message, text: str, *, reply_markup=None) -> Message:
    ...

async def safe_delete(message: Message | None) -> None:
    ...
```

Если удобнее — можно сделать функции под aiogram типы:

```python
async def edit_or_answer(message: Message, text: str, *, reply_markup=None) -> Message:
    ...

async def answer_temp(message: Message, text: str) -> Message:
    ...
```

Главное: handlers не должны вручную дублировать try/except вокруг каждого
`edit_text`.

### 2.2 Исправить основные handler'ы

Обязательные файлы:

- `bot/handlers/photos.py`
- `bot/handlers/search.py`
- `bot/handlers/settings.py`
- `bot/handlers/profile.py`
- при необходимости `bot/handlers/start.py`, `bot/handlers/matches.py`

Требования по поведению:

1. Callback-навигация должна редактировать текущее сообщение.
   Примеры:
   - `list_photos`
   - `view_photo:*`
   - `back_to_photos`
   - `back_to_profile`
   - `settings`
   - `start_search`
   - swipe like/pass после обработки

2. Фото-галерея не должна отправлять пачку сообщений.
   Текущее поведение `_send_photos_gallery()`:
   - заголовок отдельным сообщением;
   - каждое фото отдельным сообщением;
   - меню отдельным сообщением.

   Нужно заменить на компактный экран:
   - одно сообщение со списком фото и кнопками действий;
   - при просмотре конкретного фото редактировать этот экран;
   - если нужно показать изображение, использовать один media-message или
     текстовый fallback, но не отправлять весь список заново после каждого
     действия.

3. Загрузка фото:
   - временное `⏳ Загружаю фото...` допустимо, но после успешной загрузки его
     нужно удалить или заменить итоговым экраном;
   - после загрузки показать один обновлённый экран "Фото загружено / мои фото",
     а не цепочку из статуса, успеха, заголовка и N фото.

4. Поиск анкет:
   - `🔍 Ищу подходящую анкету...` должно быть временным сообщением или
     редактироваться в карточку анкеты;
   - после swipe like/pass текущая карточка должна заменяться следующей
     карточкой, а не добавлять новую ниже;
   - сообщения "Анкеты закончились / обновляю подборку / пока нет новых анкет"
     должны укладываться в один обновляемый экран.

5. Настройки:
   - `/settings` как команда может создать новый экран;
   - callback `settings` должен редактировать текущий экран;
   - успешные изменения (`✅ Диапазон возраста установлен...`,
     `✅ Максимальное расстояние...`) лучше заменять на экран настроек с
     обновлёнными значениями, а не отправлять отдельный success-message.

6. Профиль:
   - callback-навигация и успешное редактирование полей должны возвращать на
     обновлённый экран профиля/меню, а не создавать новые сообщения.

## 3. Ограничения

- Не ломать FSM создания анкеты: вопросы, где пользователь должен ввести текст
  (`имя`, `возраст`, `bio`, `город`, `интересы`), могут оставаться отдельными
  сообщениями, но callback-переходы и экраны-меню должны редактироваться.
- Не удалять пользовательские сообщения с фото/текстом без явной необходимости.
- Не менять Backend API.
- Не менять бизнес-логику свайпов, профилей, загрузки фото.
- Не ухудшать поддержку `parse_mode=HTML`.
- Учесть ограничения Telegram: нельзя заменить обычный text-message на photo
  через `edit_text`; для такого случая должен быть fallback.

## 4. Приёмочные критерии

### Ручной сценарий 1: фото

1. `/start` или `/profile` -> `Мои фото`.
2. Открыть список фото.
3. Открыть конкретное фото.
4. Вернуться назад.
5. Загрузить новое фото.

Ожидаемо:

- после входа в фото-flow в чате остаётся не больше 1-2 новых сообщений от бота;
- список фото не дублируется пачкой;
- после загрузки фото временное сообщение удалено или заменено;
- нет повторяющихся блоков "📸 Твои фото", "Фото 1", "Фото 2" отдельными
  сообщениями.

### Ручной сценарий 2: поиск

1. `/search`.
2. Лайк / пропуск нескольких анкет подряд.
3. Дождаться состояния "анкет нет".

Ожидаемо:

- карточка анкеты заменяется следующей карточкой;
- нет цепочки новых карточек после каждого swipe;
- "ищу / обновляю / нет анкет" не создают три отдельных сообщения.

### Ручной сценарий 3: настройки

1. Открыть `/settings`.
2. Изменить возраст/дистанцию/кого ищешь.
3. Вернуться к настройкам.

Ожидаемо:

- экран настроек обновляется;
- success-сообщения не копятся отдельными строками.

## 5. Техническая проверка

Обязательно выполнить:

```bash
.venv/bin/python -m ruff check bot tests
PYTHONPATH=backend DATABASE_URL=sqlite+aiosqlite:///./test.db REDIS_URL='' RABBITMQ_URL='' \
  .venv/bin/python -m pytest tests -q --tb=short
```

Если добавляются тесты для helper'а — положить их в `tests/` и мокировать
aiogram message/callback объекты без реального Telegram API.

После фикса пересобрать и перезапустить bot:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build bot
docker compose -f docker-compose.yml -f docker-compose.prod.yml logs bot --tail=120
```

## 6. Рекомендуемая стратегия реализации

1. Сначала добавить helper `bot/utils/message_editor.py`.
2. Перевести callback-heavy пути:
   - `photos.py`
   - `search.py`
   - `settings.py`
   - `profile.py`
3. Затем пройтись по `rg "message.answer|callback.message.answer" bot/handlers`
   и оставить новые сообщения только там, где это осознанно нужно.
4. Добавить 1-2 unit-теста на helper:
   - успешный `edit_text`;
   - fallback на `answer`, если edit невозможен.
5. Провести ручную проверку трёх сценариев из раздела 4.

---

## 7. Что считать готовым результатом

Готовый результат — не просто отсутствие ошибок, а заметно более чистый чат:
основные UI-состояния бота выглядят как один обновляемый экран с inline-кнопками,
а не как поток новых сообщений.
