# Шпаргалка для защиты: ConnectMe (Telegram-бот знакомств)

> Цель файла — простыми словами объяснить, что сделано, зачем и почему это стоит максимального балла.

---

## 1. О чём проект в одном абзаце

ConnectMe — это Telegram-бот для знакомств. Пользователь регистрируется,
заполняет анкету, добавляет фото, листает других людей, ставит «лайк»
или «дизлайк», получает уведомление при взаимной симпатии и
открывает чат с собеседником. Под капотом — полноценный backend на
FastAPI, очередь сообщений, фоновые задачи, мониторинг и нагрузочные
тесты. Всё запускается одной командой через `docker compose`.

---

## 2. Что умеет бот (что показать вживую)

| Шаг | Команда / действие | Что произойдёт |
|---|---|---|
| 1 | `/start` | Бот приветствует и предлагает создать анкету |
| 2 | `/profile` | Пошаговый мастер: имя, возраст, город, био, фото |
| 3 | `/search` | Показывает анкеты, кнопки «лайк / пропустить» |
| 4 | Лайк взаимный | Оба получают пуш-уведомление о мэтче |
| 5 | `/matches` | Список взаимных симпатий, кнопка «написать» |
| 6 | `/settings` | Поменять фильтры поиска или удалить анкету |

Тестовый пользователь для демо: **Яр**, `telegram_id=913011232`,
город Сириус. В базе уже сидят моки (`9_000_000_001…008`),
чтобы поиск сразу что-то показывал.

## 3. Из каких «кубиков» собран проект

Все кубики живут в одном `docker-compose` — это удобно для защиты:
поднимается одной командой.

| Кубик | Зачем нужен (простыми словами) |
|---|---|
| **Telegram-бот** (aiogram) | Принимает сообщения от пользователя, рисует кнопки |
| **Backend (FastAPI)** | Вся бизнес-логика: анкеты, поиск, лайки, мэтчи |
| **PostgreSQL** | Постоянное хранилище — анкеты, лайки, мэтчи |
| **Redis** | Быстрый кэш — чтобы не дёргать БД на каждый свайп |
| **RabbitMQ** | «Почта» между сервисами — асинхронные события |
| **Celery** | Фоновые задачи — то, что не нужно делать прямо сейчас |
| **MinIO** | Хранилище фотографий (как S3 у Amazon, только своё) |
| **Prometheus + Grafana** | Мониторинг — сколько запросов, ошибок, лагов |
| **Nginx** | Принимает входящий трафик и раздаёт по сервисам |

Полный список сервисов в `docker-compose.prod.yml`: backend, bot, db,
redis, celery_worker, celery_beat, swipe_consumer, match_consumer,
rabbitmq, minio, nginx, prometheus, grafana.

## 4. Зачем каждая технология (это и есть баллы)

> Полный реестр с путями файлов и строками — см. отдельный документ
> [`docs/технологии.md`](технологии.md).

### Redis — кэш горячих данных (+2 балла)
- Кэшируем анкеты, которые часто запрашиваются в `/search`.
- Не «костыль ради костыля»: без кэша БД задыхается на 50+ RPS.
- Используется не только для Celery → даёт **2 балла**, а не 1.
- **Где в коде:**
  - `backend/core/redis_client.py` — обёртка-клиент, метрики кэша
  - `backend/services/matching_service.py` — кэш кандидатов поиска
  - `backend/services/rating_service.py` — RatingCache, hot-rating
  - `backend/api/v1/matching.py`, `backend/api/v1/rating.py` — точки чтения/записи
  - `backend/api/v1/health.py` — health-check Redis
  - `backend/celery_app.py` — Redis как broker/result для Celery
  - `infrastructure/redis/` — конфиг сервиса

### Celery — фоновая обработка (+2 балла)
- Пересчёт **рейтинга** анкеты после свайпа — это занимает время,
  пользователь не должен ждать.
- Обработка **фотографий** — resize, генерация thumbnail.
- Отправка **уведомлений** о мэтчах.
- **Где в коде:**
  - `backend/celery_app.py` — конфигурация воркера и расписания
  - `backend/tasks/rating_tasks.py` — пересчёт рейтинга
  - `backend/tasks/photo_tasks.py` — resize/thumbnail
  - `backend/tasks/notification_tasks.py` — отложенные уведомления
  - `backend/api/v1/photos.py`, `backend/api/v1/matching.py` — `.delay()` вызовы
  - `docker-compose.prod.yml` → сервисы `celery_worker`, `celery_beat`

### RabbitMQ — асинхронные события (+2 балла)
- Свайпы летят в очередь `swipe_events`, отдельный сервис их
  обрабатывает в фоне (`swipe_consumer`).
- Мэтчи летят в очередь `match_notifications`, бот их забирает
  и шлёт пуш в Telegram (`match_consumer`).
- Есть **DLQ (Dead Letter Queue)** — если сообщение не обработалось
  3 раза, оно уходит в карантин, не теряется. Это «правильная»
  работа с очередями.
- Не только для Celery → **2 балла**.
- **Где в коде:**
  - `backend/core/mq.py` — connection-pool, publisher, базовые helpers
  - `backend/workers/base_consumer.py`, `backend/workers/swipe_consumer.py` — обработка `swipe_events`
  - `bot/workers/base_consumer.py`, `bot/workers/match_consumer.py` — обработка `match_notifications`
  - `backend/api/v1/matching.py`, `backend/api/v1/profile.py` — публикация событий
  - `infrastructure/rabbitmq/definitions.json` — exchange `dlx`, очереди `*.dlq`, x-dead-letter-routing-key
  - `infrastructure/rabbitmq/event_publisher.py`, `rabbitmq.conf`

### MinIO (S3) — фото (+2 балла)
- Все фото пользователей лежат в MinIO, а не в БД и не на диске.
- Celery-задача делает thumbnail для быстрой отдачи в поиске.
- **Где в коде:**
  - `backend/core/minio.py` — клиент, presigned URL, bucket init
  - `backend/services/photo_service.py` — upload/delete/thumbnail
  - `backend/tasks/photo_tasks.py` — фоновый resize → MinIO
  - `backend/api/v1/photos.py` — REST API загрузки/выдачи
  - `backend/models/photo.py` — модель с object_key
  - `bot/api_client.py`, `bot/keyboards/inline.py` — отдача фото в Telegram
  - `infrastructure/minio/` — конфиг бакета

### Метрики и логирование (+2 балла)
- На backend и боте поднят endpoint `/metrics` (Prometheus).
- В Grafana есть **6 готовых панелей**:
  - RPS по endpoint'ам
  - p95 latency
  - 5xx error rate
  - Бизнес-метрики (свайпы/мин, мэтчи/мин)
  - Состояние очередей RabbitMQ
  - Активность бота
- Логи через **loguru** с контекстом (telegram_id, profile_id) — не
  «Error happened», а «Ошибка в matchmaking: профиль #1234 не найден».
- **Где в коде:**
  - `backend/core/metrics.py` — Counter/Histogram/Gauge, middleware
  - `backend/core/logging_context.py` — bind контекста к логам
  - `backend/main.py` — монтирует `/metrics`, request-логгер
  - `bot/metrics.py`, `bot/main.py` — метрики бота
  - `infrastructure/prometheus/prometheus.yml` — scrape jobs
  - `infrastructure/grafana/provisioning/dashboards/connectme.json` — дашборд из 6 панелей
  - `infrastructure/grafana/provisioning/datasources/prometheus.yml`

### CI/CD (+1 балл)
- GitHub Actions: `.github/workflows/ci.yml`
- 4 job'а: lint (ruff) → tests (pytest) → build (Docker) → secret-scan (gitleaks)
- Зелёный бейдж в README.

## 6. Доп. этап: сервис уведомлений (+2 балла)

Когда два пользователя ставят друг другу лайк, происходит вот это:

```
[backend] поймал взаимный лайк
   │
   ▼
[RabbitMQ] очередь match_notifications
   │
   ▼
[bot/match_consumer] забирает событие
   │
   ▼
[Telegram] оба получают пуш-уведомление
```

Это **отдельный сервис** (`bot/workers/match_consumer.py`), не часть
бота-обработчика. Если бот упадёт — события не теряются, ждут в
очереди. Полная документация: `docs/stages/stage_notification_service.md`.

**Где в коде:**
- `backend/api/v1/matching.py` — публикация события `match_created`
- `backend/tasks/notification_tasks.py` — Celery-задача отправки пуша
- `bot/workers/match_consumer.py` — потребитель `match_notifications`
- `bot/workers/base_consumer.py` — общая логика consumer + ack/nack
- `infrastructure/rabbitmq/definitions.json` — очередь + DLQ
- `docker-compose.prod.yml` → сервис `match_consumer`

## 10. Шпаргалка вопросов от комиссии

**В: А Redis нельзя было заменить просто словарём в памяти?**
О: Нет. Backend запускается в нескольких репликах (см. `docker-compose.prod.yml`),
у каждой реплики свой процесс — словарь не делится. Redis — единая
точка кэша для всех инстансов.

**В: Зачем RabbitMQ, если есть Celery?**
О: Celery — это «отложить задачу на потом». RabbitMQ — это «послать
сигнал другому сервису». Свайп прилетает на backend, но обрабатывает
его отдельный consumer — это разные процессы, между ними нужна очередь.
DLQ страхует от потерь.

**В: Что такое DLQ?**
О: Dead Letter Queue — карантинная очередь. Если сообщение трижды
не смогло обработаться (например, БД лежала), оно уходит в DLQ,
а не теряется. Потом можно разобрать вручную.

**В: Почему Locust, а не JMeter?**
О: В `req.md` явно написано «если в другом формате — обговариваем
лично». Locust — современная Python-альтернатива, удобнее для проекта
на Python. Все CSV и метрики приложены.

**В: Где гарантия, что код не падает?**
О: pytest-тесты в `tests/`, CI зелёный (GitHub Actions). Locust
прогон — 4000+ запросов, 0 ошибок. Ручной сценарий пройдёт в Telegram
прямо сейчас.

**В: Что в логах при ошибке?**
О: Через `loguru` с `bind(telegram_id=..., profile_id=...)` —
сразу видно, кто и где упал. Не голый стектрейс.

**В: Сколько RPS держит?**
О: 50+ RPS на ключевых эндпоинтах с 0 ошибок, p95 < 200мс. Под 100 RPS
mixed профиль тоже без ошибок, но p95 уже выше SLA — узкое место в
PostgreSQL connection pool, расширяется параметром.

**В: Что с секретами?**
О: Все секреты в `.env` (в git не коммитятся), в compose проверяются
через `${VAR:?...}` — без `.env` запуск падает с понятной ошибкой.
В CI `gitleaks` сканит репо на утечки.

## 11. Если что-то не запустится на защите

1. `docker compose ps` — кто упал?
2. `docker compose logs <сервис> --tail 50` — что в логах?
3. Самые частые причины:
   - не заполнен `.env` → `cp .env.example .env`
   - порт 8005 / 3000 / 5432 занят → `lsof -i:8005`
   - MinIO без фото → `bash scripts/...` (см. `reference_minio_resync` в памяти)

## Главное в одной фразе

**Проект — не «куча технологий ради технологий».** Каждая железка
закрывает реальный кейс: Redis ускоряет поиск, RabbitMQ страхует
доставку, Celery снимает нагрузку с веб-запросов, MinIO хранит фото,
Grafana показывает, что всё живо. Если убрать любую — функционал
либо сломается, либо станет медленнее. Это и есть «обоснованное
применение» из `req.md`.

**Итог: 34 балла → оценка «5».**
