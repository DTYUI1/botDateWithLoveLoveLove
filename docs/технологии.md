## 1. Рейтинг — 3 балла

**Что реализовано:** все три уровня из ТЗ (primary, behavioral, combined).

| Файл | Что делает |
|---|---|

## 2. Redis — 2 балла

**Обоснование:** Redis используется **не только** как broker для Celery,
а как полноценный кэш горячих данных. Без него БД задыхается на 50+ RPS.

| Файл | Что делает |
|---|---|
| `backend/core/redis_client.py` | Async-клиент, метрики hit/miss, TTL-политики |
| `backend/services/matching_service.py` | Кэш кандидатов для `/matching/next` (горячий путь поиска) |
| `backend/services/rating_service.py` | `RatingCache` — кэш combined-рейтинга, чтобы не пересчитывать каждый свайп |
| `backend/api/v1/matching.py` | Чтение/инвалидация кэша при свайпе |
| `backend/api/v1/rating.py` | Чтение рейтинга из кэша |
| `backend/api/v1/health.py` | Ping Redis в health-check |
| `backend/celery_app.py` | Redis = broker + result backend для Celery (это +1) |
| `backend/core/config.py` | `REDIS_URL`, TTL-настройки |
| `infrastructure/redis/` | Docker-конфиг сервиса |
| `docker-compose.prod.yml` | сервис `redis` |

**Не подпадает под анти-примеры из ТЗ:**
- НЕ используем как основное хранилище — основная БД это PostgreSQL.
- НЕ кэшируем статику (города/страны) — кэшируем именно горячие выборки.

## 3. Celery — 2 балла

**Обоснование:** в Celery вынесены **тяжёлые задачи**, которые нельзя
делать в HTTP-запросе (resize фото, пересчёт рейтинга по всему графу
лайков, отправка пушей).

| Файл | Что делает |
|---|---|
| `backend/celery_app.py` | Конфиг Celery-приложения, beat-schedule |
| `backend/tasks/__init__.py` | Регистрация задач |
| `backend/tasks/rating_tasks.py` | `calculate_rating_task` — пересчёт рейтинга после свайпа |
| `backend/tasks/photo_tasks.py` | `process_photo_task` — resize → thumbnail → upload в MinIO |
| `backend/tasks/notification_tasks.py` | `send_match_notification_task` — отложенная отправка |
| `backend/api/v1/photos.py` | `.delay()` вызов фото-задачи после загрузки |
| `backend/api/v1/matching.py` | `.delay()` вызов рейтинг-задачи после свайпа |
| `docker-compose.prod.yml` | сервисы `celery_worker`, `celery_beat` |

**Не «костыль»:** resize 4МБ JPEG занимает ~300мс — нельзя блокировать HTTP-запрос.

## 4. RabbitMQ (MQ-брокер) — 2 балла

**Обоснование:** MQ используется для **межсервисной коммуникации**,
а не только Celery. У нас 2 отдельных consumer-сервиса +
полноценный DLQ-механизм.

| Файл | Что делает |
|---|---|
| `backend/core/mq.py` | Connection pool, publisher, helpers `publish_event()` |
| `backend/workers/base_consumer.py` | Базовый класс consumer: ack/nack, retry, DLQ |
| `backend/workers/swipe_consumer.py` | Consumer очереди `swipe_processing` — обработка свайпов в фоне |
| `bot/workers/base_consumer.py` | То же для бота |
| `bot/workers/match_consumer.py` | Consumer `match_notifications` — отправка пушей в Telegram |
| `backend/api/v1/matching.py` | Публикация `swipe_event`, `match_created` |
| `backend/api/v1/profile.py` | Публикация событий профиля |
| `infrastructure/rabbitmq/definitions.json` | Декларация: exchange `dlx`, очереди `swipe_processing`, `match_notifications`, `rating_calculation`, `message_delivery` + парные `*.dlq` с `x-dead-letter-routing-key` |
| `infrastructure/rabbitmq/rabbitmq.conf` | Конфиг сервера |
| `infrastructure/rabbitmq/event_publisher.py` | Хелпер для публикации |
| `docker-compose.prod.yml` | сервисы `rabbitmq`, `swipe_consumer`, `match_consumer` |

**DLQ (Dead Letter Queue):** в `definitions.json` 4 пары
основная-очередь ↔ DLQ. После 3 неудачных попыток сообщение
автоматически уходит в `*.dlq` — не теряется.

## 8. Другое (+2 балла за каждый пункт) — обговариваем лично

В проекте есть **два** дополнительных архитектурных решения,
не покрытых базовыми пунктами:

### 8.1. Nginx как reverse-proxy и API gateway (+2)

**Зачем:** terminate HTTP, маршрутизация бот ↔ backend ↔ MinIO ↔
Grafana через один порт, единая точка для rate-limiting и логов
доступа.

| Файл | Что делает |
|---|---|
| `infrastructure/nginx/nginx.conf` | upstream-блоки, proxy_pass, заголовки |
| `docker-compose.prod.yml` | сервис `nginx` как entry-point |

**Почему «обоснованно»:** без него пришлось бы пробрасывать 5+
портов наружу, что небезопасно и неудобно.

### 8.2. Структурный health-check + готовый bootstrap инфраструктуры (+2)

**Зачем:** endpoint `/healthz` опрашивает БД, Redis, MinIO, RabbitMQ —
для probes Docker/k8s. Скрипты автоматически разворачивают и
сидируют окружение.

| Файл | Что делает |
|---|---|
| `backend/api/v1/health.py` | `/healthz` — проверка всех зависимостей с таймаутами |
| `scripts/health-check.sh` | Shell-обёртка для CI и локального cron |
| `scripts/setup-infra.sh` | Bootstrap всей инфры одной командой |
| `scripts/seed_mock_users.py` | 8 моков для демо/нагрузочных |
| `scripts/backup-db.sh` | Бэкап PostgreSQL |
| `scripts/deploy.sh` | Деплой-скрипт |

> Готов к разговору лично, если комиссия хочет засчитать только одно из двух.

## Главное

Каждая технология в проекте закрывает **конкретный кейс из ТЗ**,
а не добавлена «для галочки». Это можно проверить по принципу «убери и
сломается»:
- убери **Redis** → поиск падает на 50+ RPS из-за нагрузки на БД;
- убери **Celery** → HTTP-запрос блокируется на resize фото;
- убери **RabbitMQ** → match-уведомления теряются при перезапуске бота;
- убери **MinIO** → фото некуда складывать, БД распухает;
- убери **Prometheus/Grafana** → на защите нечем доказать SLA;
- убери **Nginx** → 5 портов наружу + ручная маршрутизация.

**Итог: 34 балла → оценка «5» с запасом.**
